# Phase 8 — FTS5 Full-text Search & Search History / Recent Views

## Direction A: FTS5 Full-text Search

- **Architecture**: External content FTS5 virtual table (`skills_fts`) referencing `skills` table via `rowid`.
- **Tokenization**: `unicode61` — works well for both English and Chinese text.
- **Sync Strategy**: Rebuild entire index after bulk operations (`replace_all_skills`, `import_skills_from_json`). Rebuild also after individual `update_skill`. No per-row DELETE/INSERT — external content FTS5 does not support individual row manipulation reliably via `DELETE`.
- **`rebuild_fts_index()`**: Calls only `INSERT INTO skills_fts(skills_fts) VALUES('rebuild')` — no preceding `DELETE`, which caused SQLITE_CORRUPT on external content tables.
- **`query_skills`**: Search condition changed from `name LIKE ? OR description LIKE ?` to `skills.rowid IN (SELECT rowid FROM skills_fts WHERE skills_fts MATCH ?)`.
- **`search_suggestions`**: New Tauri command returning top-N matching skills for auto-complete.
- **Keyword Highlighting**: `highlightText()` utility in `lib/utils.ts` returns HTML with `<mark>` tags. Used in `SkillCard` via `dangerouslySetInnerHTML`. Source data is local files so XSS risk is acceptable.

## Direction B: Search History / Recent Views

- **Tables**: `search_history` (id, query, created_at) with max 50 entries. `recent_views` (id, skill_id FK, viewed_at) with max 30 entries.
- **`add_recent_view`**: Uses upsert pattern — if same `skill_id` exists, update `viewed_at`; otherwise INSERT.
- **`Dashboard`**: "Recently Viewed" section appears between favorites card and breakdown cards. Shows up to 6 mini-cards.
- **`SearchBar`**: Dropdown merges suggestions (top section) and search history (bottom section), separated by a divider. Glass effect via `backdrop-blur-xl`.
- **Entry Points**: Search history recorded on Enter key or suggestion/history click. Recent views recorded in `SkillDetail` via `useEffect` on `skill?.id`.

## FTS5 Caveats

- `rusqlite` needs both `bundled` and `vtab` features for FTS5 virtual table support.
- FTS5 MATCH syntax supports advanced operators (`"phrase"`, `+word`, `-word`, `AND`, `OR`).
- Simple word queries work directly. For very short single letters, FTS5 may return empty results — `unicode61` tokenizer min token size is 1 by default.
- Tests use in-memory FTS5 setup without the initial rebuild (rebuild happens via `replace_all_skills`).

## Phase 8.2 Pitfalls

### 1. SQLite schema 初始化问题
- **execute_batch 拆分**：多语句 execute_batch 在某些 rusqlite 版本上有解析问题，改为独立的 conn.execute() 更可靠。
- **CREATE INDEX 必须在列创建之后**：idx_skills_favorite 建在 avorite 列被 ALTER TABLE ADD COLUMN 之前，删库重建时会崩溃。所有依赖后期 ADD COLUMN 的索引必须移到 ADD COLUMN 之后。

### 2. 数据库列名被污染
- skill_tags 表不知什么原因混进了 	ag 列（而非 	ag_id），导致 INSERT 报 NOT NULL constraint failed: skill_tags.tag。
- 解决：在 init_db 中加 has_bad_tag 检测，发现 	ag 列存在时直接 DROP TABLE 重建。

### 3. Tauri v2 参数名转换
- Tauri v2 命令参数名默认要求 camelCase（前端），Rust 端用 snake_case 会被自动转换。
- 例如：Rust skill_id: String → 前端发 { skillId } 而不是 { skill_id }。
- struct 字段（如 AssignTagRequest { skill_id, tag_id }）保持 snake_case。

### 4. Store actions 的 async 错误处理
- Store action 内部 catch 后 set({ error }) 再 	hrow e，这样调用方可以 catch 并显示错误。
- 如果只 set({ error }) 不 throw，调用方会以为操作成功。
- TagManager 的 onClick={async () => { try { await onAssign() } catch(e) { showError(e) } }} 模式是推荐的。

## Phase 8.3b — Categorization Conflict Remediation

- Categorization history and `skills.category` are written through `rusqlite::Transaction`; a missing skill produces an error and automatic rollback instead of leaving an open transaction.
- Conflict list and count use the same `ROW_NUMBER()` CTE, ordered by `created_at DESC, id DESC`, so Dashboard totals and list contents share one rule.
- The Tauri contract is `resolve_conflicts(ResolveConflictsRequest)`; the frontend sends all selected resolutions in one invoke call while the backend commits each skill independently.
- Dashboard refreshes conflict count on mount and immediately after AI categorization finishes, keeping both the conflict card and sidebar glow current without reloading.
- Focused database coverage includes empty history, conflict detection, manual resolution, rollback, audit ordering, and a 5,000-skill performance scenario.
- Live DeepSeek end-to-end verification still requires runtime API configuration; no secret values belong in project files or memory.
- A conflict is resolved by any history entry newer than the latest AI result, even when the manual choice keeps that same AI category. Comparing only `skills.category` cannot distinguish “unreviewed” from “confirmed new.”
- Historical reasons are immutable audit text. The conflict UI suppresses legacy reasons that do not match the current UI language and shows a localized explanation; new reasons follow `settings.language` at categorization time.
- `idx_categorization_history_skill_order` supports both latest-history checks and the 5,000-skill conflict performance target.

# Phase 12 — Data backup, restore & migration safety (2026-08-08)

- **New module**: `src-tauri/src/backup.rs` — versioned backup format (format id `skillhub-backup`, version 1), full backup/restore/preview, validation, and unit tests.
- **Backup contents**: skills metadata (including category + favorite columns), tags + name-based associations, search history, recent views, categorization history, execution audit, and settings. `api_key` is deliberately excluded from the `settings` section.
- **Restore**: parse + validate (format, version, count/string bounds, required id/name) before any write; the multi-table write runs in a single rusqlite transaction and rolls back fully on failure. Idempotent via natural-key dedupe (INSERT OR IGNORE / WHERE NOT EXISTS) so a repeat restore creates no duplicate associations or audit rows.
- **Restore UI**: Settings → Backup & Restore with Create backup, Restore from backup, and Verify database. Restore shows a preview (counts per section + warnings) and requires explicit confirmation.
- **Skills upsert detail**: skills are restored with `INSERT ... ON CONFLICT(id) DO UPDATE`, NOT `INSERT OR REPLACE` — the latter deletes the existing row and (with the bundled SQLite's default foreign-key cascade) wipes dependent associations and changes rowid, breaking idempotency. This was caught by the idempotency test.
- **Corruption/migration detection**: `db::init_db` now runs `PRAGMA integrity_check` and `PRAGMA user_version`; a newer schema is refused. Before any migration it copies the raw file to `skills.db.pre-migrate-<ts>.bak`, and on a corrupt/unreadable startup it preserves `skills.db.corrupt-<ts>.bak` before the in-memory fallback.
- **Schema versioning**: `CURRENT_SCHEMA_VERSION = 1` tracked via `PRAGMA user_version`; set at the end of `init_schema`.
- **New commands**: `backup_data`, `preview_restore`, `restore_data`, `verify_database`, `get_data_directory`. Diagnostics also gained a `database-integrity` item.
- **Docs**: `DATA_DIRECTORY.md` defines install/over-install/uninstall/rollback/machine-migration behavior and the backup format.
- **Verification**: `cargo test` 46/46 pass (3 new backup tests: round-trip counts+fields, idempotency, invalid-backup rejection with no writes). `pnpm exec tsc --noEmit` exit 0.
- **KNOWN ISSUE — RESOLVED (P0-1, react-router-dom build failure)**: the previously recorded `pnpm run build` failure is fixed. Actual root cause was NOT a broken `react-router-dom` tarball but the robocopy de-referenced `node_modules`: every pnpm symlink/junction (top-level and nested) had been flattened into copies, so transitive re-exports (`react-router-dom` → `react-router`, `@tanstack/react-virtual` → `@tanstack/virtual-core`) and runtime imports (`vite` → `rolldown`) could not resolve because those transitive packages were missing at top level. Fix: re-hoisted all runtime packages to top-level `node_modules` (135 added; `@types/*` excluded — the only multi-version conflict `@types/unist@2/3` is type-only and irrelevant under `skipLibCheck` and at runtime). No version or `pnpm-lock.yaml` change was made. Verification: `pnpm exec tsc --noEmit` exit 0, `tsc -b` exit 0, `pnpm run build` exit 0 (vite built, 2690 modules), `pnpm run lint` 0 errors / 19 pre-existing warnings, `cargo build` exit 0, `cargo test` 46/46. Note: under the DSH sandbox, `vite build`'s `exec("net use")` realpath optimization hits the named-pipe EPERM boundary and needs full-access; in a normal environment plain `pnpm run build` passes.

# P0-1 / P1-3 — Remaining risks (剩余风险)

- **P0-1-R1 (node_modules 非标准结构)**: the build fix used a flat re-hoist of runtime packages to top-level `node_modules` instead of restoring pnpm's canonical symlink/junction layout. It builds and tests cleanly today, but any future `pnpm install` (dependency-tree change) should run `pnpm install --frozen-lockfile` (network is available per P0-2) to restore the canonical layout; do not keep hand-editing `node_modules`.
- **P0-1-R2 (`@types/*` 未提升)**: the flat hoist excluded all `@types/*` because `@types/unist` exists in two versions (2.0.11 / 3.0.3); type-checking currently relies on `skipLibCheck: true`. If `skipLibCheck` is ever disabled, transitive `@types/*` resolution may break — prefer a canonical `pnpm install` over disabling `skipLibCheck`.
- **P0-1-R3 (环境注意, 非缺陷)**: under the DSH sandbox, `vite build`'s `exec("net use")` realpath optimization hits the named-pipe EPERM boundary and needs full-access; in a normal environment `pnpm run build` passes.
- **P1-3-R4 (桌面 UI 验证)**: machine-migration repoint is covered by a backend regression test, but the actual desktop UI flow (Settings → change directory → re-scan → repoint, bilingual / dark / light / narrow window) is external QA not exercised in this sandbox (no GUI).
- **P1-3-R5 (skill_directory 重指向 UX 契约)**: after a migrated restore, `settings.skill_directory` still holds the old machine's path; the user must re-select a directory through the UI (no manual DB/JSON editing). This contract needs real-desktop verification. Source: `总结/phase12总结.md` 已知边界.
